# Store every user upload in S3

Status: **shipped** (2026-10-30) - implemented on `feature/s3-uploads`, pending
staging verification (see "Success looks like"). Lasting decisions live in
`docs/project/DECISIONS.md`.

## Problem

Every file a user uploads through Mautic lands on the VPS disk
(`media/files`, `media/images`, ...). Moving a client to a new VPS means
copying those folders by hand, and anything missed is silently broken:
asset downloads 404, images vanish from emails and landing pages (including
emails already sent, whose HTML embeds `https://<site>/media/images/...`).

The upstream Amazon S3 plugin (`MauticCloudStorageBundle`) does not solve
this: it is read-only, it only lets the asset form *browse* a bucket and
link to an object someone uploaded by other means (see
`docs/project/TROUBLESHOOTING.md`, "Amazon S3 plugin enabled, but new
assets never show up in the bucket").

## Goal

The VPS becomes disposable. Every upload goes to the S3 bucket; the
database keeps the reference (the object's URL or key). Moving to a new
VPS = deploy this image pointing at the same database and the same bucket
env vars. No file copying.

Success looks like: upload an asset, a builder image, a form file and a
contact avatar on server A; destroy server A; bring up server B against
the same DB + bucket; everything downloads/renders, and an email sent from
A still shows its images.

## Non-goals

- **No migration of existing local files.** Decided by the user: start
  from zero with new uploads. Files already on disk stay on disk and keep
  working as today on that server; they are *not* carried to a new VPS.
- No changes to the upstream Amazon S3 plugin / remote-asset browse
  feature. It stays as is, unrelated.
- No private storage for files/images. Everything under `media/files/` and
  `media/images/` is public-read, form uploads included (user accepted this;
  stored names carry a random 16-hex prefix but that is not access control -
  see Decisions).
- Exception: `media/dashboards/` is private (security ruling during
  implementation). Mautic reads it with its own IAM credentials; the bucket
  policy only opens `media/files/` and `media/images/`.
- Temporary/disposable files stay local: contact exports
  (`media/files/temp`), CSV import files, `media/assets` (built JS/CSS),
  cache, logs, themes, translations.
- No custom domain/CDN in front of the bucket (can be added later via a
  public-URL env var, see "Left to the builder").

## Configuration (decided)

Env vars, same pattern as the rest of this fork's EasyPanel config
(`docker/render-local-config.php`):

```dotenv
S3_BUCKET=mautic-selfhosted
S3_REGION=sa-east-1
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_ROOT_DIRECTORY=gpsdapena        # one per client, e.g. trilhasdearuanda
```

- Feature is **on only when bucket, region, both keys and
  `S3_ROOT_DIRECTORY` are all set**; otherwise Mautic behaves exactly like
  upstream (local disk). This keeps local dev / tests unaffected.
  *(Builder's-call default: requiring the root dir avoids ever writing at
  the bucket root, next to `database/`.)*
- Credentials come from env only - not from the plugin UI / DB.
- The vars must be set on **all three EasyPanel apps** (web, cron,
  worker): the worker sends emails with asset attachments, cron jobs touch
  avatars/forms. *(My call.)*
- **Mixed state is expected:** rows/HTML created before the feature was
  turned on keep pointing at local files and keep working on that server
  (asset rows stay `local`). Image pickers list **only the bucket** once
  the feature is on; old local images still render where already used but
  aren't offered for new picks. *(My call - consistent with "start from
  zero".)*

## Bucket layout (decided)

Keys mirror the local `media/` tree under the client's root directory:

| Upload | Local today | S3 key |
| --- | --- | --- |
| Assets | `media/files/<path>` | `<root>/media/files/<path>` |
| Builder / editor images | `media/images/<name>` | `<root>/media/images/<name>` |
| Contact avatars | `media/images/lead_avatars/avatar<id>` | `<root>/media/images/lead_avatars/avatar<id>` |
| Form file uploads | `media/files/form/<formId>/<fieldId>/<name>` | `<root>/media/files/form/<formId>/<fieldId>/<name>` |
| User dashboards (import/save) | `media/dashboards/...` | `<root>/media/dashboards/...` |

Public URL of an object:
`https://<bucket>.s3.<region>.amazonaws.com/<key>`.

Access: a **bucket policy** grants public `s3:GetObject` on
`arn:aws:s3:::<bucket>/*/media/files/*` and
`arn:aws:s3:::<bucket>/*/media/images/*` only; `media/dashboards/` and
`database/` stay private (dashboards are read with the IAM credentials). Don't rely
on object ACLs (new buckets have ACLs disabled). The bucket's "Block
Public Access" must allow bucket policies. The IAM user needs
`s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket`
(the last scoped by prefix if desired). Document this in
`docs/project/DEPLOYMENT.md`.

## Behavior per upload surface

The common building block is one storage service (wrapping the S3 client
already in the lock file - `aws/aws-sdk-php`; `league/flysystem` v3 is also
present, `league/flysystem-aws-s3-v3` is not yet) that knows the root
directory and can put / delete / list / build public URLs. When the feature
is off, it's a no-op passthrough so call sites keep upstream behavior.

### 1. Assets (Components > Assets, local upload; also asset API)

Files enter via the OneupUploader temp dir and `Asset::upload()`
(`app/bundles/AssetBundle/Entity/Asset.php` ~L690). Behavior wanted:

- After the upload completes (size/mime/extension already computed from
  the local temp file), push it to `<root>/media/files/<path>` and remove
  the local copy.
- **Download goes through Mautic** (`PublicController`), which records the
  download as today and then **redirects** to the S3 URL. Download
  tracking must keep working.
- Deleting an asset, or replacing its file, deletes the S3 object.
- **Assets attached to emails** (`MailHelper::attachAsset()` /
  `attachFile($asset->getFilePath())`, ~L386-697) must still attach the
  real file, not fail or attach a URL string.

*Suggested approach (builder may choose otherwise):* after pushing to S3,
store the asset as `storageLocation = 'remote'`, `remotePath = <S3 URL>`.
This reuses the existing remote-asset download path in
`PublicController::remoteRedirectResponse()` (already patched in this fork
to forward campaign query params - commit 42c9908382) for free. Side effect
to accept or avoid: editing such an asset later shows "Remote" + the URL in
the form. Deletion must only touch objects under our own
`<root>/media/` prefix, never arbitrary remote URLs a user typed.

### 2. Images uploaded in the email / landing-page builders

Three entry points, all writing to `media/images` today:

- GrapesJS: `plugins/GrapesJsBuilderBundle/Helper/FileManager.php`
  (upload, paginated media list, delete).
- Legacy editors (CKEditor/Froala):
  `app/bundles/CoreBundle/Controller/FileController.php` (upload, list,
  delete) and `Controller/Api/FileApiController.php`.
- elFinder file manager: `fm_elfinder` root in `app/config/config.php`.
  Implemented with a small custom Flysystem adapter over `MediaStorage`
  (scoped to `media/images/`), not `league/flysystem-aws-s3-v3`; uploads are
  auto-renamed on collision (`upload_overwrite=false`).

Wanted: uploads go to `<root>/media/images/...`, and **the URL returned to
the editor (and therefore embedded in the email/page HTML stored in the
DB) is the S3 public URL**. That is what keeps already-sent emails
rendering after a server or domain change. The image pickers list and
delete from the bucket (respecting `image_path_exclude`). Images that
ship with Mautic itself (flags, etc.) stay local.

### 3. Contact avatars

`LeadController` (~L854) / `AvatarHelper` / `LeadModel` (~L504) write
`media/images/lead_avatars/avatar<id>`. Move to S3 and make the avatar URL
the S3 URL. *(My call: included because the user asked for "everything
that is an upload".)* The uploaded content is checked with `getimagesize()`
before it is stored (also when S3 is off).

### 4. Form file-upload fields

`app/bundles/FormBundle/Helper/FormUploader.php` (upload, per-field /
per-form / per-submission delete; JPG rotation fix runs before upload) and
`ResultController` (~L218, ~L247: download/preview of a submitted file).
Wanted: stored in S3; downloads from the results screen and from
notification emails keep working (redirect to the S3 URL is fine - it's
public anyway); deleting a submission/field/form deletes its objects.

### 5. User dashboards

`DashboardModel` (~L126) / `DashboardController` (~L440) via
`PathsHelper::getSystemPath('dashboard.user')`. Low traffic; save, list and
import must work against S3.

## Decisions

- **Public `media/files/` and `media/images/`, form uploads included** -
  user's decision; `media/dashboards/` is private. Consequence: anyone with
  a link can open a contact's submitted file (LGPD exposure); stored names
  get a random 16-hex prefix, which only prevents guessing.
- **Per-client prefix in a shared bucket** (`S3_ROOT_DIRECTORY`) rather
  than a bucket per client - user's decision; matches the multi-client
  reuse of this stack (`OVERVIEW.md`).
- **Download stays tracked through Mautic, then redirects** - my call;
  keeps download stats and avoids streaming files through PHP.
- **Deleting in Mautic deletes in S3** - my call.
- **Off unless fully configured** - my call; upstream behavior is the
  fallback, so tests and ddev need no S3.

Promoted to `docs/project/DECISIONS.md` ("User uploads live in S3").

## Left to the builder

- Whether to add `league/flysystem-aws-s3-v3` (natural fit for elFinder
  and a single storage abstraction) or use the AWS SDK directly. If a
  dependency is added, it must be a runtime (non-dev) dependency - this
  image installs with `--no-dev` (see the dom-crawler incident in
  `TROUBLESHOOTING.md`).
- Optional extras like `S3_ENDPOINT` (S3-compatible providers) or
  `S3_PUBLIC_URL` (CDN/custom domain in front of the bucket).
- Exact wiring (decorating upstream services vs. subscribers vs.
  overriding), keeping the diff against upstream small and contained.
- Failure behavior when S3 is unreachable during an upload: the upload
  must fail visibly, never "succeed" with the file left only on local
  disk.
- Tests: unit tests with the S3 client mocked; feature off = upstream
  tests pass untouched.
